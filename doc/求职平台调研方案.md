# AI 求职助手平台 — 调研与方案设计

> 调研日期：2026-10-14（v2，经 grilling 两轮决策修订）
> 状态：方案调研稿（MVP 未开工）

---

## 1. 项目定位

一个 **AI 求职工作台**：站长（你）租服务器部署，朋友注册使用、各自填写大模型 API Key。当前**只做国内市场**（公司招聘官网采集），海外（Greenhouse/Lever/Ashby 等 ATS 公开 API）作为未来拓展方向保留。

核心链路：

```
岗位采集（官网 API / Playwright / 手动粘贴）
        ↓ LLM 结构化
      岗位库（按公司归档）
        ↓
简历库（Master Profile 结构化）
        ↓
人岗匹配（推荐值 1~100 + 通用四维理由）
        ↓
针对具体岗位的简历修改建议
```

**设计原则**（来自竞品教训、合规调研与需求确认）：

1. **人在回路**：只做"看和改"，不做自动投递。自动投递既带来封号风险，也是法律风险最集中的行为。
2. **多用户但轻量**：朋友注册使用、自带 API Key；岗位库设计为平台级共享（一个岗位只解析一次），简历/匹配结果用户私有。
3. **模型可插拔**：所有 LLM 调用走统一抽象层，支持市面上主流模型 API（DeepSeek 打底、旗舰精排），人人可用自己的 key。
4. **采集分层降级**：能用 HTTP API 就不用浏览器，能浏览器渲染就不碰招聘平台，手动粘贴 JD 永远兜底。
5. **评分体系岗位通用**：不按岗位方向特化 rubric，保证未来推荐给任何求职方向的人都能用。

## 2. 功能需求

| # | 功能 | 输入 | 处理 | 输出 |
|---|------|------|------|------|
| F1 | 多模型接入 | 各家 API Key（每用户自配） | 统一网关层，可配置、可切换 | 所有 AI 功能的基础设施 |
| F2 | 岗位采集 | 公司招聘官网 URL（或 JD 文本） | HTTP API / Playwright 抓取 → LLM 解析 → 结构化入库 | 公司 + 岗位库（含需求、任职要求） |
| F3 | 人岗匹配 | 结构化简历 + 岗位库 | 规则过滤 → 粗排 → LLM 精排 | 推荐值 1~100 + 通用四维分 + 理由 |
| F4 | 简历优化 | 某个具体岗位 + 简历 | LLM gap 分析 | 逐条修改意见（原文/建议/理由/优先级） |

**已确认的范围决策**：

- **注册制**：邀请码注册（管理员在管理界面生成/作废一次性邀请码），无开放注册入口，用户规模始终可控。
- **岗位库平台级共享**：管理员（站长）配置采集源并调度刷新，公司 + 岗位 + 解析结果全用户复用（LLM 解析成本只付一次）；用户私有的是简历、匹配结果、修改建议、API key，以及**手动粘贴的私有岗位**（不进共享库）。
- 评分维度固定通用四维（技能匹配 / 经验相关度 / 职级与薪资匹配 / 行业业务匹配），权重可配、默认均等，**不做方向特化 rubric**。
- 匹配触发：新岗位入库后自动排队打分（开关默认开、成本面板可见）+ 手动全量重算（用于简历更新后）。
- Phase 2 只输出建议清单，**不做简历成品导出**（DOCX/LaTeX/PDF 以后再说）。
- **不做**：招聘平台（Boss直聘等）采集（未来看情况）、自动投递、移动端、本地模型 Ollama（后期可选，现阶段靠脱敏模式保护隐私）。

**隐含需求**：

- 任务异步化：采集、批量匹配都是慢操作，需要后台任务队列 + 进度展示。
- 成本记账：每次 LLM 调用按用户记录 token 消耗与预估成本。
- 岗位快照：保存抓取时间和原文，content_hash 检测岗位新增/下架/变更。

## 4. 关键技术方案

### 4.1 F1 多模型接入

国内主流模型（DeepSeek、Kimi/Moonshot、GLM、Qwen/DashScope）全部提供 **OpenAI 兼容 API**，改 `base_url` + `api_key` 即可接入。

**实现**：自建 `llm.chat(messages, model, json_schema)` 抽象模块，底层用 [LiteLLM](https://github.com/BerriAI/litellm)（140+ provider 统一 OpenAI 格式，含重试/回退/成本计算）。多用户场景下每用户一张 provider 配置表（key 服务端加密落库）。

- **结构化输出是基石**：岗位解析、打分、建议全部要求 JSON。优先用 `response_format: json_schema`；不支持的家用 prompt 强约束 + 校验重试（最多 2 次）。
- **分级用模**：解析/粗排用便宜模型（DeepSeek 打底），精排和 gap 分析用旗舰模型。用户可在设置里覆盖默认分配。
- **成本记账**：`llm_calls` 表按用户记录 `{task_type, model, tokens, cost_estimate}`。

### 4.2 F2 岗位采集（已对五家目标公司完成实测调研）

采集分层（国内市场版）：

```
层 1：官网 HTTP JSON API（米哈游✓ 腾讯✓ 已实测打通）→ 首选，纯 HTTP，零渲染
层 2：官网 Playwright 渲染（字节/B站/美团）          → 次选，浏览器渲染抓取
层 3：手动粘贴 JD（永远兜底）
层 4（未来）：招聘平台登录态读取、海外 ATS 公开 API
```

#### 五家目标公司招聘官网实测结论（2026-10-14）

| 公司 | 招聘站 | 渲染 | 实测接口 | 登录要求 | 反爬风险 | 适配器路线 |
|------|--------|------|---------|---------|---------|-----------|
| 米哈游 | jobs.mihoyo.com | SPA | ✅ **已打通**：`POST https://ats.openout.mihoyo.com/ats-portal/v1/job/list`（body: `{"pageNo":1,"pageSize":10,"channelDetailIds":[1],"hireType":0}`，社招 hireType=0 共 667 岗；详情 `POST /v1/job/info`）返回职责/要求/加分项全文 | 浏览无需登录，仅投递需登录 | **低**（无签名无 cookie 校验，curl 裸测通过） | 纯 HTTP |
| 腾讯 | careers.tencent.com | SPA | ✅ **已打通**：`GET https://careers.tencent.com/tencentcareer/api/post/Query?keyword=&pageIndex=1&pageSize=10&language=zh-cn&area=cn`（现 2237 岗；详情 `GET .../post/ByPostId?postId=<id>&language=zh-cn` 含要求全文） | 浏览无需登录 | **低**（无签名，timestamp 可省略，公开教程沿用多年稳定） | 纯 HTTP |
| 字节跳动 | jobs.bytedance.com | SPA | ⚠️ 旧公开接口 `/api/v1/search/job/posts` 已变更（POST 返回 405/HTML），存在 **csrf 校验**（需先取 cookie 再带 `csrftoken` 请求头） | 浏览无需登录 | **中低**（csrf 属常规会话流程，非加密对抗；实现期用 DevTools 确认当前 XHR 路径） | Playwright 优先 |
| 哔哩哔哩 | bilibili.com/blackboard/join-list.html + jobs.bilibili.com | SPA | ⚠️ 列表页为 2.4KB 空壳，数据 XHR 加载；`jobs.bilibili.com` 的 API 需 `ajSessionId` 会话参数（实测返回 `ajSessionId不能为空`） | 浏览无需登录 | **中低**（会话参数由首页正常流程发放，非加密签名） | Playwright 优先 |
| 美团 | zhaopin.meituan.com | SPA | ⚠️ `/api/position/list` 实测返回 `{"errorCode":401,"message":"未登陆"}` —— 五家中唯一明确要求登录态的列表 API；且美团设有反爬团队（在招反爬工程师岗） | **列表 API 需登录态**（网页端匿名浏览是否走其他接口待实现期 DevTools 确认） | **中**（需复用登录态或实现期找匿名通道；有专业反爬团队） | Playwright + 登录态（最后做） |

**适配器工程形态**：

- 统一 `SiteAdapter` 接口：`fetch_list() -> [RawJob]` + `fetch_detail(id) -> RawJob`，HTTP 型与 Playwright 型实现同一接口，上层（LLM 解析、入库）无感知。
- HTTP 型（米哈游/腾讯）：直接 requests 调接口，1~2s 间隔翻页。
- Playwright 型（字节/B站/美团）：headless 渲染列表页（滚动/翻页）→ 进详情页抽正文；美团如需登录态则复用站长/用户自己的已登录浏览器（CDP connect，不模拟登录、不破解）。
- 每站点一份适配器配置（JSON），站点改版时只改配置；**所有适配器失败时手动粘贴兜底**。

#### 合规要点

依据最高检 2025 年刊文与最高法指导性案例 263 号（用户授权后处理自己在平台有权获取的数据，不构成不正当竞争）：

- 风险从低到高：公开 API（米哈游/腾讯接口即公开数据接口） < 官网页面渲染 < 需登录态读取 < 破解加密/批量高频。
- 自守措施：只采公开浏览可见的岗位信息、限速 1~8s、不逆向加密参数、不对外分发原始数据、采集结果仅用于个人求职决策。
- 结论：**米哈游/腾讯路线 ≈ 零风险；字节/B站/美团为低风险但需克制频率；本项目全程不触碰"破解"类技术。**

### 4.3 F3a 简历导入与解析

两段式（对齐 SmartResume / Resume-Matcher）：

1. **文本抽取**（本地零 token）：PDF→PyMuPDF/pdfplumber，DOCX→python-docx，Markdown 直读；扫描件降级 OCR（可选后期）。
2. **LLM 结构化** → Master Profile JSON（basic_info / education / work / projects / skills / certificates / self_summary）。

- 支持多份简历（master + 定制版），打分默认用 master。
- **脱敏模式**：姓名/手机号/身份证本地加密存储，调用云端 LLM 时替换占位符（打分不需要真实身份信息）。

### 4.4 F3b 人岗匹配打分

三阶段流水线：

```
岗位库(活跃岗位) → ① 硬规则过滤（免费：城市/经验差/硬门槛，排除也给理由）
                 → ② 粗排（便宜：关键词/FTS 或 embedding，取 Top N）
                 → ③ LLM 精排（贵：rubric 打分，强制 JSON）
```

**精排输出 Schema**（通用四维）：

```json
{
  "score": 78,
  "verdict": "值得投递",
  "dimension_scores": {"技能匹配": 85, "经验相关度": 80, "职级与薪资匹配": 65, "行业/业务匹配": 70},
  "reasons": "…",
  "matching_points": ["…"], "gaps": ["…"],
  "score_basis": "rubric 锚点说明"
}
```

- **权重可配（默认均等）**：用户可调四维权重，总分 = Σ(维度分×权重)；维度分由 LLM 输出、总分由代码加权计算（跨模型更稳定）。
- **稳定性**：temperature=0；rubric 锚点（90+/75-89/60-74/<60）；结果按 `hash(resume_id+job_id+resume版本)` 缓存。
- **触发**：新岗位入库自动排队打分（可开关，默认开，成本面板可见累计消耗）+ 简历更新后手动全量重算。
- **成本**：单次精排 ≈ 3k tokens；50 岗全量 ≈ 15 万 tokens，DeepSeek 级约 ¥0.3~0.5。个人使用可忽略，多用户下靠共享解析结果 + 缓存控制总成本。

### 4.5 F4 简历修改建议

输入：岗位 JD + 简历 + 已有匹配结果（直接复用 gaps 列表）。

输出：逐条建议（`section` 定位到简历字段、`action` 改写/新增/补充关键词、`original`/`proposed`/`why`/`priority`）+ `missing_keywords` + **`honesty_warnings`（防编造红线：建议必须可追溯到简历原文或用户补充的事实，参考 ApplyPilot forceTruthfulness 设计）**。

## 5. 系统架构（多用户服务器部署版）

### 5.1 技术栈

| 层 | 选型 | 理由 |
|----|------|------|
| 后端 | Python 3.12+ + FastAPI | 与解析/爬虫/LLM 生态重合；AutoApply 验证过 |
| 前端 | Vue 3 + Vite | 同上 |
| 数据库 | **PostgreSQL 16**（多用户直接上 PG；暂不需要 pgvector，FTS5/关键词粗排够用，岗位过千再评估向量） | 多用户并发 + 服务器部署 |
| 异步任务 | **arq（Redis）**：采集与批量打分必须后台化；MVP 期间也可先用 FastAPI BackgroundTasks 过渡 | 轻于 Celery |
| 采集 | requests（HTTP 型适配器）+ Playwright（渲染型适配器） | 按站点选择 |
| LLM 层 | 自建抽象 + LiteLLM | 见 4.1 |
| 鉴权 | **邀请码注册制**：管理员生成一次性邀请码 → 朋友凭码注册（用户名/邮箱+密码）→ JWT 会话；无开放注册 | 用户规模可控，防陌生人消耗采集/Playwright 资源 |
| 部署 | Docker Compose（web + postgres + redis + playwright 容器）部署到云服务器；Caddy 反代自动 HTTPS | 一键起停 |
| 服务器 | **尚未租用**。建议二选一（部署时定）：① 境内轻量云 2核4G（¥50~100/月）+ 域名 ICP 备案（数周，无 deadline 不构成阻塞），Playwright 采国内站快；② 香港/境外轻量（免备案、即开即用），HTTP 型适配器无感，Playwright 渲染稍慢 | chromium 需 ≈2G 内存，4G 起步 |

本机环境（已验证）：Python 3.13.5 / Node 24 / Docker 28 / pnpm 11 均可用。

### 5.2 数据模型（多用户）

```
users(id, email, password_hash, is_admin, invited_by_code, created_at)
invitation_codes(code, created_by, used_by, used_at, is_revoked)   -- 管理员生成/作废
```

## 6. MVP 分期路线图

业余节奏、无 deadline；每期独立可用、可验收。**先把匹配闭环跑通，再上采集**。

### Phase 0 — 骨架 + 多用户 + 多模型 + 手动导入
- **状态**：✅ 已完成（2026-10-27 收尾，`specs/platform-core/spec.md` 为规格基线）
- FastAPI + Vue 脚手架；PG 建表；**邀请码注册/登录（JWT）+ 管理界面基础（用户/邀请码管理）**；用户 provider 配置界面
- LLM 网关：`chat()`、JSON Schema 校验重试、按用户成本记账
- 手动创建公司 + 粘贴 JD 文本 → LLM 解析入库（共享岗走 job_postings，普通用户粘贴走 user_manual_jobs）
- 上传 PDF/DOCX 简历 → 文本抽取 + LLM 结构化 + 脱敏
- **验收**：两个账号各自配 key，粘贴 5 个 JD 全部解析成规范结构化数据；简历解析字段准确。

### Phase 1 — 匹配打分闭环
- **状态**：✅ 已完成（2026-11-03）。实现落点：`backend/app/scoring.py` + `backend/app/api/matches.py` + `Jobs.vue`/`Settings.vue`。
- 硬规则过滤 + LLM 精排（通用四维 + 权重配置）+ 结果缓存
- 新岗位入库自动排队打分（可开关）+ 手动全量重算；成本面板
- 岗位列表按推荐值排序，详情页展示维度分/理由/匹配点/缺口
- **验收**：50 岗 × 1 简历全量打分，单用户成本 < ¥1；同输入重复打分结果一致（缓存）。
- **实现说明（与计划的差异）**：① 按用户决定**只做手动触发**（全量/单岗/改权重重算），不实现"新岗位自动排队"；② 缓存键 = (用户, 简历, 简历版本, 岗位)，重算需显式 `force`；③ 实测单次精排 1200 输入 + 180 输出 tokens，50 岗约 6.9 万 tokens，远低于 ¥1（价格表未配置，`llm_calls` 只记 token 不估价）；④ 重复打分一致性由缓存键 + 唯一索引保证，已有测试覆盖。

### Phase 2 — 简历修改建议
- **状态**：✅ 已完成（2026-11-04）。实现落点：`backend/app/suggestions.py` + `backend/app/api/suggestions.py` + `Jobs.vue`（匹配详情内）。
- gap 分析 + 逐条建议 + honesty_warnings
- **验收**：任一匹配结果可生成建议；每条建议可定位到简历具体段落；人工抽查无编造经历。
- **实现说明（与计划的差异）**：① 按用户确认**按单个岗位生成**（输入是某条匹配结果），不做整份简历通用体检、不做成品导出；② 每条建议绑定 `match_result_id` 做缓存键，重新打分后旧建议自然失效；③ 防编造做了两道：prompt 红线 + 确定性定位校验（`original` 在简历文本里找不到就追加 `honesty_warnings`，空 `original` 视为"需用户补充事实"）；④ 只读不回写简历画像。

### Phase 3 — HTTP API 采集（米哈游 + 腾讯）
- 两个 HTTP 型适配器 + 公司页一键"拉取全部岗位"→ 批量解析入库
- content_hash 变更检测（新增/下架/修改）
- **验收**：两家官网全量岗位（约 2900 个）入库，字段完整；重复抓取正确识别变更。

### Phase 4 — Playwright 采集（字节 → B站 → 美团，按此顺序）
- Playwright 渲染框架 + 统一 SiteAdapter 接口
- 字节、B站适配器（匿名渲染）；美团最后做（如需登录态则 CDP 复用）
- scrape_sources 调度定期刷新
- **验收**：目标公司官网岗位全量入库；站点改版时仅改适配器配置即可恢复。

### 未来拓展（不在本期）
- 海外 ATS 公开 API（Greenhouse `boards-api.greenhouse.io/v1/boards/{token}/jobs?content=true`、Lever `api.lever.co/v0/postings/{company}?mode=json`、Ashby `api.ashbyhq.com/posting-api/job-board/{org}`）
- 招聘平台登录态辅助采集（CDP 复用，参考 boss-zhipin-scraper）
- 本地模型 Ollama、简历成品导出、向量粗排

## 7. 风险清单

| 风险 | 等级 | 缓解措施 |
|------|------|---------|
| 站点改版致适配器失效 | 高（必然发生） | 适配器配置化 + 手动粘贴永远兜底；content_hash 让失效可发现 |
| 美团等站点需登录态/反爬升级 | 中 | 放最后做；CDP 复用真实登录态；不行就只支持手动粘贴该公司 JD |
| 多用户服务器安全（简历数据泄露） | 中 | key 加密落库、简历文件不进 git/备份加密、HTTPS 强制、邀请码注册可控规模 |
| LLM 评分不稳定 | 中 | rubric 锚点 + temperature 0 + 缓存 + 代码层加权总分 |
| 建议编造经历（信誉风险） | 高 | forceTruthfulness 约束 + 建议必须引用原文 + honesty_warnings |
| API 成本失控 | 低 | 分级用模 + 按用户记账 + 缓存 + 岗位解析结果共享 |
| 服务器运维负担 | 低 | Docker Compose 单机；PG 定时备份；朋友量级（<20 人）无压力 |
