## 2. 需求覆盖（对照 proposal / specs/platform-core 的 4 条 Requirement）

1. **匹配打分流水线**：`scoring.filter_jobs`（经验差 >2 年、学历不足，附理由；解析失败放行）→ `rank_candidates`（技能重叠 0.6 / 标题 0.25 / 城市 0.15，默认取 20）→ `score_one`（四维 0-100 + 锚点 + 强制 JSON，`temperature=0`）。✅
2. **缓存与成本**：唯一键 `(user_id, resume_id, job_ref_type, job_ref_id, resume_version)`；命中直接返回不调模型；`force` 覆盖同一行而非新增；每次调用写 `llm_calls`（task_type=score）。✅
3. **权重与排序**：`users.score_weights`（空=均等 25），`combine` 代码加权 + clamp + 缺失维度记录；`GET/PUT /api/matches/weights`；`/api/jobs/{shared,mine}?sort=score`。✅
4. **结果可见性**：列表/详情均按 `user_id` 过滤，详情含四维/理由/匹配点/缺口/岗位快照；前端岗位页展示并可展开详情。✅

## 3. 代码审查要点

- **鉴权与隔离**：`matches` 全部端点经 `get_current_user`；单岗打分对共享岗校验 `is_active`、对私有岗校验 `user_id`，他人岗位返回 404；列表与详情均带 `user_id` 过滤（`test_matches.py::test_results_are_isolated_between_users` 覆盖）。
- **路由顺序**：`/weights` 与 `/weights/current` 声明在 `/{match_id}` 之前，否则会被路径参数吞掉（实现期已发现并修正，现按此顺序）。
- **同名遮蔽**：任务运行器 `run_match_job`/`run_match_run` 与路由处理器曾同名，导致 `enqueue(runner=...)` 解析到错误函数（`TypeError: missing 'body'`）；已把处理器改名为 `score_single_job`/`run_full_scoring`，URL 不变。测试覆盖了这条路径。
- **事务**：`score_one` 遇 `IntegrityError`（并发写入同键）回滚后改为覆盖，不向上抛；`run_scoring` 对单岗异常只记 `failures`，不中断整轮。
- **任务可见性**：`Task.params["result"]` 回写 summary，`GET /api/tasks/{id}` 暴露 `result`，前端据此聚合计数；`retry` 复用同一 `params`，不泄漏他人任务（仍按 `user_id` 过滤）。
- **成本**：一次全量最多 `limit`（默认 20，上限 100）次调用；`llm_calls.cost_estimate` 仍为 0（价格表未配置，与 Phase 0 决策一致，不引入假数字）。

## 4. 遗留（非阻塞，建议后续处理）

1. `score` 任务在 `BackgroundTasks` 内串行调用 LLM，`limit=100` 时单任务可达数分钟且无进度上报；Phase 2 引入 arq 时应改为分片 + 进度字段。
2. 权重以中文维度名作 JSON 键，若将来改维度命名需写数据迁移；已在 `DIMENSIONS` 常量集中定义，改动面可控。
3. 硬规则只用启发式年限/学历解析，解析不出即放行——这是"宁可多花 token 也不误杀"的有意取舍，代价是脏 JD 不会被过滤。
4. `frontend/dist` 按 `.gitignore` 不入库，部署需构建；`python:3.13-slim` 镜像仍未在本机构建验证（Phase 0 起就存在的遗留）。
