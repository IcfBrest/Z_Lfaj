## 2. 代码检查要点

1. **快照 vs 关联**：`applications` 不建到 `job_postings`/`user_manual_jobs` 的外键，岗位删除不会级联删记录（`test_delete_job_keeps_application` 之外，岗位表无反向关系）；`source_url` 快照依赖 `scoring.JobView.source_url` 新字段。
2. **时间处理**：SQLite 取回的是 naive datetime，`days_since_update` 按 UTC 补时区，`test_days_since_update_handles_naive` 覆盖。
3. **幂等**：同状态 PATCH 不追加事件，但允许更新备注并刷新 `last_activity_at`（避免"改了备注却仍报停滞"）。
4. **终止态**：`rejected`/`withdrawn` 不可再流转；`stats` 的 `stale` 只统计非终止态，`active` 同理。
5. **错误码**：未知岗位 / 非本人私有岗位 → 400；他人记录 → 404；非法状态 / 终止态流转 → 400；重复投递 → 409 且 body 带 `application_id`。
6. **前端错误处理**：`api.js` 现在把结构化 `detail` 的 `message` 提到 `Error.message`，并保留 `status`/`detail`，409 分支据此拿到已存在的 id 并直接把岗位标成「已投递」。

## 4. 非阻塞遗留

1. 没有「撤销投递记录」入口（只有状态改成已放弃），误投只能改状态；后续可加删除。
2. 时间线只有状态变更与备注，没有面试时间/轮次字段；真正做面试跟踪还需要 `interview_at` 之类的结构化字段。
3. 停滞阈值固定 7 天（`STALE_DAYS`），未做成用户可配。
4. `stats` 没有按公司/来源聚合，也没有转化率（投递→面试）统计。
5. 前端列表一次性拉 `limit=500` 用于「已投递」标记，记录多了需要分页或按岗位批量查询接口。
